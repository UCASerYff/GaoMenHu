# 源码与本地文件恢复

本说明区分公开源码、正式发行包与本地私有文件。仅补充恢复说明和安全归档时，不改变程序、版本号或构建号，也不需要重装应用。

## 恢复来源与边界

| 来源 | 可恢复内容 | 边界 |
| --- | --- | --- |
| 源码仓库 | `Sources/`、`Scripts/`、`Tests/`、`VERSION`、公开说明与最终 PNG 图标 | 包含重建应用所需的项目源文件；不包含本机数据或凭据 |
| GitHub Release | 当前正式 DMG 与对应 SHA-256 文件 | 可下载原始发行包；`Release/` 目录本身不进入 Git 源码 |
| 本地私有归档 | 私人开发规则、需要保留的本地文件及核验清单 | 不会随 Git 克隆恢复，须单独保管 |

[源码仓库](https://github.com/UCASerYff/GaoYouJian)与[当前发行包](https://github.com/UCASerYff/GaoYouJian/releases/latest)承担不同恢复用途。源码归档可以重建程序；需要原始发行包时，应下载 Release 资产并核对随附校验文件。

## 原创图标的恢复链

- `Assets/AppIcon.png` 是已经提交的最终原创图稿，包含透明外围与黑底白字设计。它是恢复当前图标的实际来源。
- `Assets/IconDesign.txt` 记录设计与编辑提示词。提示词用于说明设计过程；恢复现有图标无需再次调用图像生成服务，也不依赖重新生成结果与原图一致。
- `Scripts/MakeIcon.swift` 将 PNG 缩放为各尺寸图像并封装成 ICNS，不重画字形。
- `Assets/AppIcon.icns` 是派生产物，按 `.gitignore` 排除是预期行为。干净克隆中没有该文件时，`Scripts/build.sh` 会从 PNG 自动生成，再将 PNG 与 ICNS 一起装入应用。

因此，无需为了让工作区显示干净而删除本地图标，也无需强行把 ICNS 加入 Git。若本地 ICNS 有需保留的改动，应先保留原件与校验副本；在新的克隆目录核验生成结果，避免覆盖工作目录中的文件。

## 干净克隆与构建

当前构建目标为 Apple Silicon、macOS 14 或更高版本；构建环境需要 macOS、可用的 macOS SDK 和开发工具。项目不依赖第三方 Swift 包或 Node 包。

在不存在的目标目录中克隆待核验版本。以 V1.10 为例：

```sh
git clone --branch v1.10 --single-branch https://github.com/UCASerYff/GaoYouJian.git GaoYouJian-v1.10
cd GaoYouJian-v1.10
./Scripts/build.sh
```

这会编译程序、生成缺失的 ICNS，并在克隆目录的 `Release/` 生成 DMG 和 SHA-256 文件。构建脚本使用自己的临时目录并在结束时清理，不启动应用、浏览器或测试窗口。不要先从现有工作目录复制被忽略的 ICNS 或其他本地文件，否则无法核验 Git 源码是否独立完整。

`Scripts/install.sh` 是另一项操作：它会替换已安装程序并启动应用。仅检查干净源码能否重建时，不运行安装脚本，也不自动执行冒烟测试。

重建包的哈希可能受工具链、签名及打包元数据影响。应分别记录源码版本、构建结果、图标与应用内容核验，以及下载 Release 原包的校验结果，不能仅凭一次构建成功就声称安装版、发布包或真实收发业务均已通过验证。

## 仍需私下保管的内容

`AGENTS.md` 是本地开发规则，已被忽略。私人规则和个人路径不应为了 Git 状态一致而上传公开仓库。可将原文件的副本与 SHA-256 清单保存在已忽略的 `Backups/` 中，核验副本与原件一致，并保留原件及既有备份。

邮箱资料、身份与关联平台、邮件缓存、附件、草稿、偏好设置及已有安全备份也不属于公开源码。GitHub 克隆或下载 DMG 不能恢复这些内容，需由本地数据备份负责；备份须另行核验完整性，不能把缺失或无法读取的资料当作空白覆盖。文件维护归档不能代替完整的用户数据备份。

密码、授权码、OAuth 令牌及私有客户端配置不得写入源码、公开日志、发行包或公开核验记录。钥匙串凭据继续由系统钥匙串保存，本项文件归档不导出或更改凭据。

归档不删除原文件，不清理既有备份，也不通过强制追踪被忽略文件来制造“完整”。需要跨机器恢复私有内容时，应单独保存私人归档，不能依赖公开 GitHub 仓库。

## 程序版本与维护文档

V1.10 的程序版本为 `1.10`，构建号为 `110`。`v1.10` Release 对应发布时的固定源码提交；之后仅更新说明或核验记录时，`main` 可以包含较新的文档提交，无需移动发布标签或替换既有程序包。

对照源码、安装版与 Release 时，应检查发布标签所指提交、`VERSION`、应用版本与构建号，以及相关文件内容。不能仅因 `main` 多了文档提交便判定发布不一致。只有实际程序或构建资源发生变化并正式交付更新时，才执行版本递增、数据保护、安装及发布流程。
